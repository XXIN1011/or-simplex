# 运筹学计算器（Operations Research Calculator）

一个面向**教学**的运筹学求解器，覆盖**线性规划（大 M 法单纯形法）**、**灵敏度分析**与**整数规划**。
与常见的“只给答案”的求解器不同，它把算法的**每一步中间过程完整摊开**给学生看：
单纯形法的每一张迭代表、灵敏度分析在原最优表上的判断、整数规划四种方法各自的过程。

手机优先设计，单文件、零依赖、可离线；同时它也是一个**标准的 Node 工程**：
算法层是可以 `require` 的库，还带一个命令行入口。

## 功能

**首页**列出三个模块：**单纯形法** / **灵敏度分析** / **整数规划**，各用一条 hash 路由
（`#/simplex`、`#/sens`、`#/ip`），手机上刷新、后退、加到桌面都能正常工作。

### 单纯形法

- 支持 `max` / `min` 以及 `≤` / `≥` / `=` 任意组合的约束
- 自动识别并处理三类边界情况：**无可行解**、**无界解**、**多重最优解**
- 负数右端项自动整行取负并翻转关系符（保证初始基可行）
- `min` 问题自动按 `max` 求解后还原目标值

### 灵敏度分析（场景式）

先解出基准最优解，再选一种变化按**教材做法**分析——不是把题改掉重解，而是在
原最优表上判断、继续迭代。

按**徐玖平、胡知能《运筹学（第四版）》（科学出版社）第 2 章**的小节对照：

| 教材小节 | 本应用中的场景 | 前置判断 | 判断不通过时 |
|---|---|---|---|
| 2.5.1 右边系数 | 改右端项 | 重算 `x′_B = B⁻¹b′` | **对偶单纯形法** |
| 2.5.2 非基变量系数 | 改目标系数（非基变量部分） | 只重算 `σ′_j = c′_j − z_j` | 原始单纯形法 |
| 2.5.2 非基变量系数 | 改技术系数（x_j 非基的列） | 只重算该列的 `σ′_j = c_j − c_B·(B⁻¹P′_j)` | 原始单纯形法 |
| 2.5.3 变量增加 | 增加一个变量 | 新变量的检验数 `σ′ = c′ − c_B·P` | 原始单纯形法 |
| 2.5.4 基变量系数 | 改目标系数（基变量部分） | **σ 整行重算**：`σ′ⱼ = σⱼ − Δ·(B⁻¹Pⱼ)_k` | 原始单纯形法 |
| 2.5.4 基变量系数 | 改技术系数（x_j 是基的列） | **整张表重算**（B 与 B⁻¹ 都变） | 原始/对偶单纯形法，两者同坏时重新求解 |
| 2.5.5 约束条件增加 | 增加一个约束 | 当前最优解是否满足它 | **对偶单纯形法** |
| 2.6.1 参数线性规划·变量系数 | 参数线性规划（变量系数） | `σⱼ(λ) = σⱼ + λ·τⱼ ≤ 0` 交成 λ 区间 | 区间端点处原始单纯形法换基 |
| 2.6.2 参数线性规划·右边系数 | 参数线性规划（右边系数） | `x_B(λ) = B⁻¹b + λ·B⁻¹e ≥ 0` 交成 λ 区间 | 区间端点处对偶单纯形法换基 |

> 教材把「改系数」按**是不是基变量**拆成两节（2.5.2 / 2.5.4），因为**判据完全不同**：
> 非基变量的系数只出现在它自己那一列的检验数里；基变量的系数进的是 `c_B`，而
> `zⱼ = c_B·(B⁻¹Pⱼ)` 每一项都含 `c_B`，所以 **σ 的整行都要重算**。教材这两节把
> `c_j` 与 `a_ij` 放在一起讲，本应用的输出也按这个方式分块。

输出沿用单纯形法那套迭代表（含三重高亮与逐步讲解），所以「新最优解怎么来的」
一目了然。

**边界与退化情形也如实交代，不硬算：**

- 改完之后原最优基的**基矩阵变成奇异**（列线性相关）→ 说明它不再能充当一组基，改为从标准初始基重新求解
- **可行性与最优性同时被破坏** → 原始单纯形法要求右端项非负、对偶单纯形法要求检验数非正，两种局部迭代法都用不上，教材的做法是重新求解
- 参数线性规划中 **右端项在 λ 范围内会变号** → 建表时的「整行取负」会随之翻转，模块在该临界值处停下并提示，越界部分请手工复核
- 参数线性规划中，基里残留的人工变量必须**恰好为 0**（它一旦随 λ 变成非零，就说明原约束没有被真正满足），所以该基的 λ 区间应当**钉成一点**。这里踩了第二层坑：同一个基会被「向上」「向下」两次行走各记录一遍，而这条限制最初只夹了当前行走方向 —— 另一个方向记下来的那份区间仍然过宽，合并时取的恰好是它，于是把**无可行解**的 λ 区间当成最优区间报了出去。表现是随机对拍**约一半的运行会失败**（且永远锁定在同一道含人工变量的题上），修法是两个方向都钉、并在钉完后立刻判一次空区间。

### 整数规划

输入**任意**整数规划题（每个变量分别指定 连续 / 整数 / 0-1），自动判定四种方法各自能不能用，
**能用的把完整计算过程全部输出，不能用的一律不输出、只说明为什么**。

| 方法 | 适用条件 | 输出内容 |
|---|---|---|
| 图解法 | 恰好 2 个决策变量、且有可行域 | 可行域 + **整数格点** + 松弛最优解（橙点）与整数最优解（绿点）对比 |
| 分枝定界法 | 松弛问题有最优解（几乎总是） | 逐结点的附加约束、松弛解（非整数分量加粗）、界、以及「为什么分枝 / 为什么剪掉」；每个结点还可展开看它自己的单纯形迭代表 |
| 割平面法 | 全整数 + 全 ≤ 约束 + 数据为整数（教材的标准形式） | **Gomory 割的逐刀推导**（从哪一行读出来、小数部分、割的系数），以及加割后用对偶单纯形法把表调回可行的每一步 |
| 隐枚举法 | **所有**变量都是 0-1 | 标准化（负目标系数的 x_j = 1−y_j 替换）+ 完整的枚举表：每个点的目标值、**过滤条件**是否通过、逐条约束的检查结果与结论 |

**规模保护**：隐枚举要枚举 2ⁿ 个点。引擎默认对 ≤ 36 个变量的题目都能算，但**输出**会按规模收口 ——
枚举点超过 4096 个时不再默认全跑，而是提示按用户勾选的方法输出（正是为了避免卡顿）；
枚举表超过 300 行只铺「通过过滤条件、真正检查过约束」的那些点。

**不会把「没跑完」说成「最优」**：分枝定界有结点上限（300）。一旦触顶，结论会明确写成
「目前找到的最好整数解，不能保证是全局最优」，而不是照旧标「最优解」。

### 教学特性

| 特性 | 说明 |
|---|---|
| 完整单纯形表 | 每一轮迭代的系数矩阵，含松弛变量 `s`、人工变量 `a` |
| 符号化大 M | 检验数按教材写法显示为 `7M - 4` 这类形式，而非近似大数 |
| 三重高亮 | 入基列（蓝）、出基行（橙）、枢轴元素（黄底橙边） |
| 自动讲解 | 每张表下自动生成 `① 选入基 → ② 比值检验（列出每个 θ 的计算）→ ③ 枢轴变换` |
| 输入体验 | 系数格默认留空、显示淡灰的 `0`：点进去直接打字（不必先删掉那个 0），什么都不填就按 0 计算 |
| 标准化 | 求解前先展示「原问题 → 标准型」的完整变换：min 转 max、加减松弛/剩余变量、引入人工变量 |
| 图解法 | 2 变量时自动画出可行域、目标函数等值线与最优顶点（内联 SVG） |
| 对偶解 | 由最终基算出影子价格 `y = c_B·B⁻¹`，并标出哪些约束还有余量 |
| 灵敏度区间 | 保持最优基不变时 c 与 b 的允许变化范围；基变量额外给出「c 每 +1，z* 变化多少」 |
| 参数线性规划 | 含参数 λ 时给出一张「λ 区间 → 最优基 → x(λ) → z(λ)」的分段表 |
| 退化提示 | 最小比值 θ = 0 时明确指出这一步不会改善目标值 |
| 符号说明 | 可折叠地解释 x/s/a、σ、M、基变量、z 的含义 |
| 深色模式 | 跟随系统 `prefers-color-scheme` 自动切换 |
| 溢出提示 | 表格超宽时提示可左右滑动 |

## 使用

**网页版**：直接用浏览器打开 `index.html`，或访问线上版本

**https://xxin1011.github.io/or-simplex/**

在手机上：浏览器打开 → 菜单「添加至桌面」，即可获得图标、全屏、离线可用的 App 体验。

**当库用**（Node ≥ 18）：

```js
const or = require('or-simplex');                 // 仓库内也可 require('./src/index.js')

const res = or.solve({
  direction: 'max',
  c: [2, 3],
  constraints: [
    { coef: [1, 2], rel: '<=', rhs: 8 },
    { coef: [4, 0], rel: '<=', rhs: 16 }
  ]
});
// res.status === 'optimal'，res.objective === 14，res.solution === [4, 2]
// res.steps 是每一张单纯形表（含入基/出基/θ/枢轴），res.dual 是影子价格
// res.sensitivity 是 c 与 b 的允许变化区间

console.log(or.format.report(res, problem));      // 纯文本完整报告
or.solveInteger({ ...problem, vtypes: ['int', 'int'] });   // 整数规划
or.analyzeScenario(problem, scenario);                     // 场景式灵敏度分析
or.analyzeParametric(problem, scenario);                   // 参数线性规划
```

只要算法层也可以按模块取：

```js
const { simplexSolve } = require('or-simplex/src/core/simplex.js');
const { fmtNum } = require('or-simplex/src/core/format.js');
```

**命令行**：

```bash
node src/cli.js '{"direction":"max","c":[2,3],"constraints":[{"coef":[1,2],"rel":"<=","rhs":8}]}'
node src/cli.js --file 题目.json          # 从文件读
cat 题目.json | node src/cli.js           # 从标准输入读
node src/cli.js 题目.json --json          # 直接输出结果 JSON（脚本里接管道）
node src/cli.js 题目.json --no-tables     # 只要标准型 + 结论 + 对偶 + 灵敏度
node src/cli.js 题目.json --integer       # 按整数规划求解（四种方法的适用性与结论）
```

退出码：`0` = 得到最优解；`1` = 无界 / 无可行解 / 未收敛 / 输入非法（脚本里可直接判）。

> **`index.html` 为什么必须在仓库根**：GitHub Pages 以仓库根为发布目录，入口只能是
> `/index.html`；挪进子目录，线上地址就会从 `https://xxin1011.github.io/or-simplex/`
> 变成 `.../子目录/`。所以 `src/build.js` 读写路径是分开的：读 `src/`，写 `../index.html`。

> **算法只有一份**：单纯形法的迭代内核只有 `src/core/simplex.js` 一处实现，
> 场景分析、参数线性规划、整数规划都通过 `require` 复用它（`ratioTest` / `pivot` / `solveStandardForm`），
> 不存在两份实现悄悄分叉的可能；`scenario-test.js` 的「建表一致性自检」会逐元素比对两边建的标准化矩阵。

### 分层与扩展点

```
web/*.js ──require──▶ core/{simplex,scenario,integer,format,sensitivity}
                          │
                          ├─▶ core/parse ──▶ core/model
                          ├─▶ core/{util,format,errors}
                          └─▶ core/model
```

- **单向依赖**：`web → core`，`core` 内部只允许「上层依赖下层」，没有任何环；
  `model` 是最底层（不 import 任何东西），`format` 只依赖 `util`。
- **禁止跨模块碰内部变量**：每个文件只导出少量公开函数，其余变量都是文件作用域私有。
- **扩展点（开闭原则）**：迭代内核被拆成 4 个可替换的纯函数 ——
  `selectEntering(form)`（入基规则）/ `ratioTest(form, e)`（比值检验）/ `pivot(form, r, e)`（枢轴变换）/
  `solveStandardForm(form, opts)`（主循环，接受 `opts.selectEntering` 与 `opts.maxIter`）。
  要加对偶单纯形、两阶段法，只需在自己的模块里组合这几个函数，
  **不必改动 `core/simplex.js` 里任何一行数值代码**。`test/unit/simplex.test.js` 里用一个
  自定义入基规则（Bland 最小下标规则）跑通了同一道题，作为这条扩展点的回归。
- **异常在 `core/errors.js` 统一收口**：对外仍保留老契约（输入非法 → `{ok:false,message}`；
  结论 → `status` 字符串），新调用方则可以拿 `LPError(code, message, detail)` 按 `code` 分支。

### 视觉主题（极光底 + 全玻璃）

CSS 分三层：① `html` 上的基质色；② `body::before` / `body::after` 两层**固定定位**的极光与斜纹织构；③ 一组 `--gl-*` 玻璃令牌 + 若干 `backdrop-filter`。**所有承载面都是玻璃** —— 品牌区、模块卡、正文卡、表格、按钮、结论徽章、底部标签栏，没有一处例外。四条硬约束（`src/template.html` 里有详细注释，改前务必读）：

- **`body` 必须保持透明，基质色放在 `html` 上。** `z-index:-1` 的伪元素绘制在 `body` 自身背景**之下**，`body` 一旦带实色底，极光会被整块盖住，玻璃就退化成白卡片（这个坑实测踩过：极光写得再艳，量出来仍是 `#f4f4f8` 一片灰）。
- **承载文字的玻璃厚度有硬下限。** 极光是**会漂移的动画**，同一处文字背后的颜色会随时间变艳，所以必须按最坏情况算：极光最强处的底亮度约 0.387，`--fg2` 要在上面过 4.5:1，白填充不能低于约 `.58`。浅色取 `.70`（留余量），深色因为用的是浅色文字、对底亮度要求更低，取 `.55` 更透 —— 这就是「两套主题各自调优」，不是「同一套配方反转」。
- **不要让文字直接压在没有承载面的极光上。** 模块页标题区与页脚提示原本就是裸压的，实测只有 4.09 / 4.30:1，已各补一块 `.78` 的玻璃垫底。
- **主按钮不用高饱和实心。** 「求解」是**玻璃描边**（低饱和染色 + 强调色描边 + 强调色文字），与次要按钮靠**色相**而非明度区分：它仍是全页唯一的强调色块，但不靠亮度和饱和度抢视线。旧版是亮蓝渐变 + 同色光晕的实心块，既刺眼，又和全玻璃界面冲突。

两套主题的差异是刻意做出来的：**浅色 = 更厚的玻璃 + 更淡的极光**；**深色 = 更透的玻璃 + 更饱和的极光**。分段控件的选中态也是分开设计的 —— 浅色是「白胶囊 + 蓝字」，深色是「实心强调色 + 深字」（深色下白玻璃会被下层叠成中灰，蓝字只剩 1.9:1，实测过）。

底部导航的当前模块高亮由**单个 `.tb-pill` 元素**承担，切模块时用 `transform` 平移过去，而不是「旧的消失 + 新的出现」。位置由 `src/web/router.js` 的 `movePill()` 设定（首次定位会临时关掉过渡，否则开屏会看到它从最左滑过去）；缓动用标准 ease-out，实测 30 帧采样里 19 个不同位置、单调递增。

`prefers-reduced-motion` 下极光漂移与所有过渡都会停止（样式表末尾的全局 `*{transition:none!important}` 兜住），滑动指示器也吃这条规则。

> 曾尝试做「真折射」（canvas 位移图 + SVG `feDisplacementMap`，即 GitHub 上那些 iOS 26 Liquid Glass 复刻项目的做法），实现并量测后**放弃**：折射要有高频背景才看得见，而本页背后只有一层渐变；调到勉强可见时位移量（10px）与斜纹周期（9px）同量级，周期性纹理互相挤压出摩尔纹，正常尺寸下比不折射更不精致。结论与复现方式记在 `src/template.html` 的注释里。

## 关于正确性

线性规划求解器的错误往往很隐蔽——绝大多数题都能算出“看起来对”的答案。因此本项目用多道独立关卡验证：

1. **算法层**：2000 道随机题（刻意混入高比例 `≥`/`=` 约束与负右端项）与 scipy 的 HiGHS 求解器对拍，**目标值、问题状态、解向量可行性三层全部一致**。
2. **行为快照**：`test/algorithm/deep-snapshot.js` 把每道题的**每一次迭代、每一个表格格子、每一段显示文本**都哈希成一个指纹。重构前后各跑一次、`diff` 为空，就等于「算法行为逐字节未变」——这比只比最终答案严格得多（迭代方向写反、边界条件给错都可能碰巧给出同一个最优值）。
3. **单元测试**：`test/unit/` 逐模块验接口与数学性质 —— 例如对偶解不写死数字，而是用**中心差分扰动**独立验算「影子价格 = 最优值对右端项的偏导数」；σ 行不抄实现，而是在测试里**独立重算** `c_j − c_B·P_j` 再核对。
4. **界面层**：Chrome 无头浏览器在真实手机视口下跑 98 项回归，覆盖路由、标准化、图解法、对偶解、灵敏度区间、场景分析、技术系数、参数线性规划、整数规划四方法、退化提示、0 变量/0 约束等边界与输入交互，验证渲染正确且无 JS 报错。
5. **移动端可用性**：脚本化实测所有触摸目标 ≥ 44×44、正文对比度达 WCAG AA、图解文字不越界、求解按钮无需滚动即可点到。这几项各由独立脚本把关（见上），改完随时可重跑。
6. **灵敏度区间**：区间是「恰好」的，用两道独立关口确认——① 在区间内取样，z 必须等于线性预测值（基变量用 `z₀+Δcⱼ·xⱼ`、右端项用 `z₀+Δbᵢ·yᵢ`），交给 scipy 复算；② 在区间外取样，代数上重算 `x_B` 与 σ，原最优基必须**已经失效**（否则说明区间取窄了）。
7. **场景式灵敏度分析**：判据只有一条但足够强——**场景分析给出的新最优解，必须与「把题改成新样子后用 scipy 从头重解」的结果完全一致**。120 道基准题 × 5 类场景（改 c / 改 a_ij / 改 b / 加约束 / 加变量）+ 2 个专挑基变量与非基变量下手的补例 = **700 个随机算例**，状态（最优/无可行/无界）与最优值逐项比对。
8. **参数线性规划**：结论是「λ 落在某段区间内时最优基不变，该基给出 x(λ)、z(λ)」，这句话本身要能被检验，而不是只看答案对不对（多最优解与退化会让目标值碰巧对上）。所以对每一段区间取 3 个 λ，要求：① 该段声称的最优基在这一点上**仍然可行**（`B⁻¹b(λ) ≥ 0`）且**仍然最优**（σ(λ) ≤ 0）；② 目标值等于 λ 的一次式；③ 等于从头重解的结果。再加**端点紧致性**：刚越过端点 0.05，原基必须已经失效（否则说明区间切窄了）。共 **1110 个抽样点 + 431 次紧致性检查**，全部交 scipy 独立复算。
9. **整数规划**：判据是**与暴力枚举逐项对拍**。分枝定界、割平面、隐枚举各自与「把整数变量逐个枚举、其余交单纯形法」的参考答案比对（含 0-1、纯整数、混合整数三类，各 100~400 道随机题）。

这一路验证确实揪出了若干真缺陷，都写在这里备查：

- 右端项为负的约束会被整行取负，而按标准化后的 b 算出的影子价格没有换算回用户输入，导致这类约束的符号反掉
- 最优基里残留取值为 0 的人工变量时，只要求它“≥ 0”而不要求“= 0”，会把实际上无可行解的右端项算进允许区间内
- 大 M 法在“含人工变量的扩展问题”上迭代，当入基列无正系数时不能一律判无界——若此时人工变量仍留基取正值，正确结论是**无可行解**
- 对偶单纯形的比值检验只用了检验数的常数项、忽略了 M 项，导致会挑中人工变量入基（最终答案碰巧还对，但中间解已不是原问题的可行解）
- 参数线性规划中，右端项含参数时 λ 一旦越过 `b_i(λ) = 0`，「整行取负」这个标准化动作就会翻转，而 λ 系数是按 λ = 0 的形式固定换算的 → 越界后的区间全错。修法不是硬算，而是把「标准化形式本身成立」也当成一条 λ 约束，撞上就停并说明
- 参数线性规划中，基里残留的人工变量沿着某个方向会变成正值 → 该方向上新条件无可行解，必须把这段截断在 λ = 0（与上面 b 区间那条是同一个坑的另一面）
- 整数规划隐枚举法在最小化问题上曾把比较符号写反，报出错误答案（用户报告后修复；现在最小化题会把目标系数整体取负化成求最大，表头另行标明 z 是原题口径）

## 算法说明

采用**大 M 法**。人工变量在目标函数中罚 `-M`，`M` 以符号形式（系数对 `(常数, M 系数)`）参与运算，比较时按 `M → +∞` 的字典序进行。这样既能得到教材级的标准显示，又避免了用 `1e9` 之类大数近似带来的数值精度问题。

参数线性规划里 λ 的仿射量也用同样的「系数对」结构表示（`(常数, λ 系数)`），复用了同一套线性运算；但它与 M 不同 —— λ 是个有限的实数参数，所以比较时不能套用 `M → +∞` 的字典序，而是先解出一段 λ 区间再在端点处换基。
