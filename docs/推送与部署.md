# 推送与部署

项目通过 GitHub Pages 发布，仓库根目录的 `index.html` 为网站入口。发布分支与目录以仓库的 Pages 设置为准，当前发布分支为 `main`。

## 1. 推送前检查

所有命令在仓库根目录执行。先检查分支、改动范围及远程连接：

```bash
git status --short
git branch --show-current
git ls-remote origin refs/heads/main
npm run verify
```

确认提交内容包含所需源码、文档和最新构建产物。不要将个人信息、访问密钥、认证缓存、设备配置或临时文件加入版本控制。

远程连接失败时，先区分网络、认证和仓库权限问题，再检查当前环境的 Git 配置。不要将个人网络配置写入项目文档，也不要在日志中输出认证信息。

## 2. 提交与推送

选择本次改动涉及的文件暂存，检查暂存区后提交：

```bash
git diff --cached --check
git diff --cached --stat
git commit -m "说明改动及原因"
git push origin main
```

只在确认需要提交全部改动时使用 `git add -A`；部分提交使用 `git add` 明确选择文件。不要强制加入被忽略的本地文件。

推送成功后核对远程提交：

```bash
git rev-parse HEAD
git ls-remote origin refs/heads/main
```

远程 `main` 的提交哈希应与本次发布提交一致。推送返回成功不等于自动检查或网站部署已经完成。

## 3. 认证与提交身份

使用 GitHub 支持的认证方式，通过系统凭据管理器、SSH agent 或 CI 的受保护配置管理认证材料。配置提交身份时，使用维护者自行选择的公开身份或 GitHub 提供的隐私邮箱。

- 不在仓库、命令示例或排错日志中写入真实认证材料。
- 不在公开文档中记录个人账号配置、凭据位置、访问权限明细或提取凭据的操作。
- CI 只授予任务所需权限；发布日志与附件也属于信息披露检查范围。
- 若误提交了真实密钥，应先撤销或轮换，再处理历史记录；只删除当前文件不能使已公开的密钥失效。

## 4. 持续集成

`.github/workflows/verify.yml` 在 `main` 推送、拉取请求及手动触发时运行两项检查：

| 任务 | 检查内容 |
|---|---|
| `verify` | 构建产物一致性、静态检查、单元测试、算法回归、UI 回归及无障碍和图解边界审查 |
| `crosscheck` | 生成随机题库，执行七类 SciPy 对拍并验证失败与空题库的退出码 |

两项任务均须通过。遇到求解器状态分歧时，按 [验证手册](验证手册.md) 复核，不能将真实失败当作版本差异忽略。

UI 检查失败时，先阅读 Actions 中的诊断，再按需下载日志附件。浏览器启动失败和页面断言失败应分别排查。

## 5. 部署与线上复验

Pages 有独立的部署任务。发布完成需同时满足：远程提交正确、持续集成通过、Pages 部署成功、线上页面为目标版本。

部署或缓存刷新尚未完成时，等待相应任务结束后再验证。使用当前环境的 Pages 地址运行：

```bash
node test/ui/verify-ui.js "<PAGES_URL>" --quiet
node test/ui/audit.js "<PAGES_URL>" --quiet
```

将 `<PAGES_URL>` 替换为仓库 Pages 设置中的网站地址。检查线上版本时可使用禁止缓存的请求；不要仅凭本地页面或一次推送返回值判断发布结果。
