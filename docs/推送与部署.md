> 线上只有一个地方：**GitHub Pages** —— https://xxin1011.github.io/or-simplex/
> 推 `main` 即自动重建（约 50~65 秒 CDN 延迟）。
> **不要往 Netlify 推**：那边已解绑删除；Netlify 免费版 300 额度/月是硬上限
> （一次生产部署 15 额度），耗尽会把整个团队所有站暂停到下个周期。
> 用户已经把线上地址发给同学用了，**链接不能换**。

## 1. 先探代理 —— 这是最容易失败的地方

用户机器上有两个加速工具：**Clash**（监听 7897）与 **Steam++**（劫持 hosts 把 github 指向 127.0.0.1）。
git 到 github.com 的可达性会在「直连 / 走代理」之间来回变：

```bash
git ls-remote origin main       # 通了才推；不通就是代理没就位
```

- **通了** → 保持现状直接推；
- **不通** → 别急着让用户开 Clash：先试纯直连重试 2~6 次（有时反而直连能过）：
  ```bash
  for i in 1 2 3 4 5 6; do git -c http.proxy= -c https.proxy= ls-remote origin main && break; sleep 3; done
  ```
- 两种都不通再让用户开 Clash，**不要反复硬重试**（会刷一屏失败日志）。

> 顺带：`curl` 在这台机器上有 exit 23 的毛病，会把 `&&` 链断掉 —— 串命令用 `;`。

## 2. 提交与推送

```bash
export GIT_TERMINAL_PROMPT=0                  # 防止卡在凭据提示
npm run verify                                 # 推之前必须全绿（见 docs/验证手册.md）
git add -A
git commit -m "……"                             # 中文，说清「改了什么 + 为什么」
for i in 1 2 3; do git push origin main && break; sleep 5; done
```

**推送后必须核实远程真的收到了**（不要只看 `git push` 的返回码）：

```bash
git ls-remote origin main        # SHA 应当等于 git log --oneline -1 的短 SHA
```

## 5. CI

`.github/workflows/verify.yml` 在 push 与 PR 时跑两件事：

1. **verify**（门禁）：构建 + 产物一致性（`git diff --exit-code -- index.html`）、静态检查、
   单元 + 8 套算法回归、UI 回归 133 条断言；失败时上传 `preview/logs/` 作为 artifact。
2. **crosscheck**（参考性，`continue-on-error`）：装 numpy/scipy，生成题库后跑六个对拍脚本。

线上部署**不需要**这些 job 参与 —— GitHub Pages 有自己的部署流程，仓库根就是发布目录。
CI 红了先看日志：门禁 job 红 = 真的有问题；crosscheck job 红大概率是 scipy 版本差异
（见 `docs/验证手册.md` 第 6 节），本地仍要手跑一遍确认。
